# 实验与验收说明

本项目评估单个原生 SC2 玩家内部的功能协作：经济、建设生产、侦察作战三个 Agent 控制同一人族势力。实验不声称原生多玩家组队，也不将沙盒结果视为真实游戏结果。

已有自动化测试覆盖 Mock/协议、模型适配和本地沙盒。历史专项测试中，原生 Qwen3-8B 的基础任务三个固定种子均通过，扩张供给与升级备战各有一个模型样本通过。后续 `b5c474…` 给定 Marine 参考版本在三图各获一局原生 Victory，同配置 Simple64 复验自然 Defeat；三模式统计对照仍未完成。这些是不同任务与版本的记录，不合并为通用成功率。当前结果见 [演示结果](DEMO_RESULTS.md)，完整历史见 [验证记录](VERIFICATION.md)；以下介绍执行方法和判定口径。

## 1．先确认环境与证据类型

在启动工作台的同一环境执行：

```bash
python -m sc2_harness doctor
python -m sc2_harness serve --host 127.0.0.1 --port 18890
```

随后使用另一个终端运行实验命令。`doctor` 不调用模型，不运行游戏；预检通过仍需确认地图能加载、原生观察可取得、工具确实改变游戏状态。

| 后端 / 策略 | 合法用途 | 不可据此得出的结论 |
| --- | --- | --- |
| sandbox / scripted | 检查网页、工具接口、持久化与控制 | SC2 启动成功、LLM 有效 |
| sandbox / llm | 检查真实模型与结构化工具闭环 | 模型在 SC2 中完成任务 |
| sc2 / scripted | 验证真实引擎与工具，建立规则基线 | LLM 协作有效 |
| sc2 / llm | 真实模型在真实 SC2 中执行 | 仍需逐局证据确认任务与胜负 |

原生适配器保留引擎版本、build 和玩家信息；相关运行目录中可检查 `native-engine.json`、游戏 worker 日志与可用回放。网页允许导出配置、事件、snapshots、指标和回放。对于无法启动的对局，错误记录就是事实，不应填成一次胜利或忽略不报。

离线留存一局允许导出的证据：`python scripts/fetch_evidence.py --url http://127.0.0.1:18890 --run-id <32位运行ID> --frame`，默认保存到 `runtime/evidence/{run-id}`，包含逐文件 SHA-256 清单；该命令不控制实验，原生帧不可用时明确记录。

## 2．固定任务及完成条件

默认 `Simple64`、人族、内置 VeryEasy 人族对手。完整对战地图可更换，但对照组必须一致。当前三 Agent 的工具都按人族实现，不能仅修改种族名称便当作支持其他种族。

`build_and_scout` 通过条件由 [evaluation.py](../sc2_harness/evaluation.py) 定义：

1. 工人数达到 14。
2. 完成至少 1 座补给站。
3. 完成至少 1 座兵营。
4. 陆战队员数量达到 4。
5. 侦察单位实际到达敌方出生区域。

里程碑会记录达到时的游戏时间。曾经达到后再发生战损，不抹掉已达到的里程碑；需结合终局和事件判断完整经过。五项完成即该专项任务 `success`，不表示赢下整局游戏。

`full_match` 以原生引擎终局为准：`Victory → success`、`Defeat → failure`、`Tie → incomplete`；轮数或游戏时间预算耗尽但没有终局为 `incomplete`。

运行状态 `completed` 表示实验运行器结束，不自动等于任务 `success`。`stopped / error / incomplete` 分别保留，不合并成“通过”。具体判定随代码版本保存，不在实验中途修改目标。

### 长程任务：以阶段依赖增加难度

任务声明见 [missions.py](../sc2_harness/missions.py)，判定见 [evaluation.py](../sc2_harness/evaluation.py)。新任务增加扩张、供给、产能与升级之间的依赖，不以“运行得更久”作为完成条件。以下均是实验设计，**不是已经跑出的成绩**：

| 任务 | 阶段 1 | 阶段 2 | 阶段 3 | 建议预算：轮数 / 游戏秒 / 每轮步进 |
| --- | --- | --- | --- | --- |
| `expansion_logistics` 扩张与资源供给 | 14 工人、1 完成补给站、1 完成兵营 | 已知距开局位置超过 16 的资源簇；24 工人、2 个完成且相距至少 12 的基地 | 2 完成精炼厂、整局累计采气 200 | 180 / 900 / 224 loops |
| `army_readiness` 步兵产能与升级备战 | 同上 | 2 完成兵营、1 完成工程站、整局累计采气 100 | 人口上限至少 30；完成步兵武器 1 级后，同时拥有 12 名陆战队员 | 240 / 1200 / 224 loops |
| `expansion_and_victory` 扩张后赢下对局 | 同上 | 已知距开局位置超过 16 的资源簇；24 工人、2 个完成且相距至少 12 的基地 | 原生引擎报告 `Victory` | 360 / 2400 / 224 loops |

预算是启动实验的建议，不会自动增加默认运行预算，也不保证当前策略能完成；模型等待消耗现实时间，不消耗这里的游戏秒。比较配置时，各组使用相同任务和预算。命令例如：

```bash
python -m sc2_harness evaluate --backend sc2 --policy llm \
  --map AbyssalReefLE --scenario expansion_logistics --seeds 7,19,41 \
  --max-rounds 180 --game-seconds 900 --advance-loops 224 \
  --output runtime/expansion-logistics-llm.json
```

三个长程任务推荐完整对战地图 `AbyssalReefLE`，该图的资源与扩张工具条件已由原生脚本验证；这不替代真实模型验收。网页切换任务时会把默认地图或上一任务的推荐地图换成新推荐图，用户另行输入的地图保留；基础及旧任务仍推荐 `Simple64`。使用其他地图开始统计前，应先验证资源布局与扩张命令可行，不能从短程任务通过直接推断双基地条件。

判定遵守以下规则：

- 完成前置阶段后才评估并锁存后续目标；解锁时已实际存在的设施或单位可以计入，累计采气指整局累计值。
- 每个数量门槛必须在某次观察中同时存在，例如 12 名 Marine，不能把先后生产后阵亡的 6+6 相加；排队、在建、工具接受和模型自述均不算完成。门槛曾达到后允许锁存，各个目标不要求在同一时刻首次达到。
- 基地检查己方已完成的 `COMMANDCENTER / ORBITALCOMMAND / PLANETARYFORTRESS` 实际坐标。原地重复建两个基地不能通过；缺少坐标不能推断已扩张。
- 资源位置可用性依据 `map.expansions` 中实际已知坐标与固定的开局 `map.start` 距离判断（严格超过 16）；不会用后来建成的基地反向排除候选，也不从地图名或预设坐标猜测。位置来自原生引擎的中立单位 snapshot，开局可能已经报告符合条件的资源点，因此**位置已知不等于 Agent 实地侦察发现**。该门槛只能证明扩张资源位置在观察中可用，不能单独证明侦察协作有效；缺少相关字段记未知。
- 采气使用引擎 `score.collected_vespene`，花掉气体不抹去采集记录；当前库存不能替代累计采气。研究使用 `upgrades.completed`，研究订单存在或进度 99% 不能算完成。缺少字段记未知，不能补填为通过。
- 备战任务的 12 名 Marine 仅在观察到武器 1 已完成之后才计数。先拥有 12 兵、阵亡后才研究完成不能通过；须至少有一帧同时满足升级完成与 12 名已完成 Marine。该门槛达到后可以锁存，后续损失不抹去历史达标记录。
- 备战末阶段同时给经济角色至少 30 人口上限的供给目标，避免生产角色仍需造兵时，经济角色因本阶段无目标而提前等待。人口上限取实际 `supply_cap`，在建补给不计；这不是预先指定补给站建造顺序。该目标显式声明 `maintain=true`：历史达标记录仍锁存，但当前阶段人口上限受损降到 30 以下时，角色目标重新出现实际差值、经济角色重新参与；其他未声明维持的目标不因此重复执行。
- `Defeat` 在所有任务中优先判为 `failure`，即使数量目标曾全部达到。扩张后获胜任务需要先满足扩张阶段；只有原生胜利、却缺扩张证据时仍为 `incomplete`。经济或备战专项通过，也不代表赢下对局。

每项及每阶段保存首次**观察到**达标的游戏时间；这不是未采样到的引擎瞬时完成时间。未达目标时间为 `null`。阶段完成数、阶段内进度和总目标进度分别报告，部分进度不能改写成完成。

轮数、游戏时间预算、手动停止或运行错误使未完成目标保留 `censored=true` 和结束原因；这表示只观察到截止时仍未达标，不能把截止时间填成达标时间。原生败局单列失败，不混入预算删失。运行器的错误/停止状态仍需单独报告，不能把运行错误当成策略输掉游戏；原生 `engine_result` 与任务 `outcome` 始终并列保存。

模型接收当前阶段、本角色专属目标、实际差值及未知字段，不接收预先指定的动作顺序。当前角色目标已经达到时允许空动作，避免为“必须出动作”重复建设；其他角色仍需维持必要供给、生产和防御。

启用执行指导时，阶段切换会提供当前观察中的交接事实，并从下一次输入移除旧阶段的角色历史与团队消息；原始 Trace 不删除。相同阶段保留有界历史，消息带轮次、阶段及游戏时间。原生胜利仍待达成的阶段提供持续职责说明，不能把“进入 victory 阶段”当作已获胜。关闭执行指导时保留原有输入历史，作为整体执行指导的对照；它不是只关闭一条提示的单变量实验。

以上三个长程任务的声明版本为 `2`：扩张任务增加已知资源位置门槛，备战任务增加升级与部队数量同时成立门槛。旧版本历史记录保留原判定，不把新版条件追写为旧局已通过。

## 3．三种模式做同种子对照

固定游戏版本、地图、对手、工具、可见信息、步进量、任务与预算。在 LLM 两组中还需固定模型、生成设置、历史限制及超时。模型采样仍可能不确定，**相同种子不保证每局完全相同**，应做多次重复并保留每次结果。

建议三组：

| 组别 | 配置 | 主要用途 |
| --- | --- | --- |
| A．规则脚本 | `policy=scripted` | 测环境、工具和预置策略基线 |
| B．LLM 无通信 | `policy=llm`，关闭通信 | 测独立角色决策 |
| C．LLM 有通信 | `policy=llm`，开启通信 | 与 B 比较通信带来的变化及额外开销 |

当前 scripted 策略不会产生真实 Agent 对话，所以 A 组开启通信开关不等于出现合作消息。功能角色、工具与共享观察在三组中保持一致；这不是“单 Agent 对多 Agent”的实验。

另可单独对照状态感知执行指导：默认 `execution_guidance=true`，网页可取消“状态感知执行指导”，CLI 使用 `--no-guidance`。该开关改变机械可用性与阶段/角色目标投影，不替模型决定动作；对照时固定其他条件，不能把“开指导且开通信”与“两者都关闭”的差别全部归因于通信。

下面的种子、60 轮及 300 秒是示例实验配置，不是性能指标，也不保证完成任务。需要增加预算时，三组一起修改并记录。

```bash
# A：真实 SC2，规则脚本。
python -m sc2_harness evaluate --backend sc2 --policy scripted \
  --map Simple64 --scenario build_and_scout \
  --seeds 7,19,41 --max-rounds 60 --game-seconds 300 \
  --no-communication --output runtime/compare-scripted.json

# B：真实 SC2，模型，无通信。
python -m sc2_harness evaluate --backend sc2 --policy llm \
  --map Simple64 --scenario build_and_scout \
  --seeds 7,19,41 --max-rounds 60 --game-seconds 300 \
  --no-communication --output runtime/compare-llm-no-communication.json

# C：真实 SC2，模型，有通信。
python -m sc2_harness evaluate --backend sc2 --policy llm \
  --map Simple64 --scenario build_and_scout \
  --seeds 7,19,41 --max-rounds 60 --game-seconds 300 \
  --output runtime/compare-llm-communication.json
```

每条命令依次运行其种子列表，默认工作台一次只运行一局。`evaluate` 导出逐局数据及样本数、成功数，不自动生成跨组三模式结论。输出文件分开保存，避免覆盖上一组。更严谨的比较应交替执行 B/C 的重复实验，减少服务器负载、模型服务状态随时间变化的影响。

## 4．每局记录什么

至少保留：

- 源码版本、依赖/游戏 build、地图、种子、任务、策略与通信开关。
- 模型名称、输入输出 token、实际调用/失败数、生成设置和预算；不保存认证凭据。
- 任务结果、游戏终局、逐项里程碑、轮数、游戏时间和现实耗时。
- 长程任务各阶段完成数/进度、首次观察达标时间、未完成项及删失原因；原生胜负另列。
- 指令提议、验证拒绝、引擎接受、后续观察效果及其关联。
- 原始公共模型响应、有效观察/历史、协作消息、错误和有效动作记录。
- 可用的 `.SC2Replay` 和 snapshots；原生 RGB 是否实际输出单独记录。

运行指标中的延迟 p50/p95 是该局已记录成功决策的耗时分布，单位以字段为准；`latency_p50_ms / latency_p95_ms` 为毫秒。它们不包括全部失败请求，也不等于三 Agent 一整轮的端到端延迟。比较时应同时报告实际调用样本数、失败数和墙钟时间，不能只摘一个分位数。脚本延迟不是模型推理延迟。

`round_decision_latency_p50_ms / round_decision_latency_p95_ms` 另记整轮决策等待；与角色有效决策延迟分开展示。`command_rejection_rate` 的分母是提议指令数，零提议时为未知而不是 0%；`stage_completion_rate / milestone_completion_rate` 分别按实际已达标阶段数、里程碑数计算，不能使用 Agent 的自评。

报告建议使用下表，未测项填“未测”，不要填示意成绩：

| 组别 | 计划 / 实际局数 | success / failure / incomplete / error | 各里程碑完成数 | 游戏时间 | 现实耗时 | 模型调用与失败 | token | 指令接受 / 拒绝 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A．脚本 | 未测 | 未测 | 未测 | 未测 | 未测 | 不调用模型 | 不适用 | 未测 |
| B．LLM 无通信 | 未测 | 未测 | 未测 | 未测 | 未测 | 未测 | 未测 | 未测 |
| C．LLM 有通信 | 未测 | 未测 | 未测 | 未测 | 未测 | 未测 | 未测 | 未测 |

成功率需明确分母。可以同时报告“全部启动尝试的任务成功率”和“成功启动后的任务成功率”，并列出启动/推理错误，不能静默删去失败样本。

## 5．验收时区分这些状态

| 层次 | 证据 | 不能替代的内容 |
| --- | --- | --- |
| 提议 | Agent 给出工具和参数 | 参数合法、能够执行 |
| 验证 | 权限、参数、预算和冲突检查 | 引擎已执行 |
| 引擎接受 | 对应命令的 `accepted` 回执 | 单位/建筑已经完成 |
| 观察效果 | 后续状态出现单位、完成建筑或位置变化 | 整个任务或整局胜利 |
| 任务结果 | 实际状态满足专项验收条件 | 完整游戏获胜 |
| 游戏终局 | 引擎报告 Victory/Defeat/Tie | 实时对抗能力和跨地图泛化 |

暂停、模型超时、无效动作、模型不可达、进程退出、历史实验重开等属于故障检查。验证需要记录触发条件、返回错误、清理结果和剩余进程，不必为了好看的结果自动重试整局。没有显式授权和实验配置时，不切到其他模型、脚本或沙盒补出成绩。

## 6．时钟、回放与展示

当前模式为全局手动步进：三个功能 Agent 基于一轮观察决策，运行器仲裁并提交动作，再推进整个游戏。模型等待期间我方和敌方都不推进。网页“游戏时间”和“现实耗时”不是同一指标；暂停和推理会增加后者。

原生 RGB 必须有真实 `/frame` 输出才能称为原生画面。战术 Canvas 只是观察状态可视化，历史 snapshots 只是状态重建。即使界面能播放这些状态，也不能声称已实现游戏视频直播。原生 replay 需要对应游戏版本与地图，在游戏中另行播放。

未来接入团队 Harness 时可复用这些环境、工具和证据标准，再比较新的决策实现。原生多玩家队友合作是不同范围，需要额外验证原生玩家槽位、阵营、独立可见信息、会话及同步，不由当前三功能 Agent 实验自动覆盖。
